# MochiLog Windows — Developer notes

User-facing setup and troubleshooting steps are in the [Japanese and English user guide](USER_GUIDE.md).

WinUI 3 companion app for MochiLog's optional iOS/iPadOS 27 wireless analytics transfer. This repository is an alpha under active development.

The Windows app collects Apple analytics logs and sends them to the iPhone or iPad MochiLog app. Parsing and record storage remain on the mobile app. The Windows installer includes its collector and app runtimes, so users do not need Python, .NET, or the Windows App SDK installed separately. **The current alpha is not independent of Apple's Windows device software:** first-time USB trust and OS RemotePairing use Apple's mobile-device USB stack, supplied by Apple Devices or classic iTunes. The installer neither includes nor installs this stack. The installer registers an uninstaller in Windows Settings. Windows and Mac companions do not exchange data with each other.

Settings can start MochiLog when the user signs in to Windows and keep it in the taskbar tray after the window is closed. With tray mode enabled, a sign-in launch starts hidden, double-clicking the tray icon or launching MochiLog again opens the window, and **Quit MochiLog** in the tray menu stops collection and transfer. Disabling tray mode restores normal window closing. Both settings default to off.

The **Battery logs** page lists pending and delivered raw files with export controls. By default, a file is deleted as soon as the mobile app acknowledges it. Enabling **Keep logs after delivery** retains acknowledged files for up to 500 MB and one month by default; both limits are configurable. Archived files can be exported, deleted, or manually queued for resending. Pending files are protected from retention cleanup and manual deletion. To receive a queued resend, open MochiLog on the paired iPhone or iPad and tap **Receive Now** if needed. Windows does not parse the log contents.

For local development, build `src/MochiLog.Windows/MochiLog.Windows.csproj` on Windows with the .NET 10 SDK. The project uses the Windows App SDK and WinUI 3. The user-facing installer is built with `scripts/build-installer.ps1`; it bundles the Python collector, .NET runtime, Windows App SDK files, and license notices into `Build/MochiLog-Windows-Alpha-Setup.exe`. The in-app license viewer lists MochiLog, every resolved NuGet package, every Python package in the collector build environment, and the bundled .NET 10.0.12 and Python 3.13 runtime licenses and notices. Update `resources/RuntimeLicenses/` when the bundled runtime version changes. If an upstream package does not ship its license text, its declared license and project URL are shown. It installs for the current user and registers its uninstaller in Windows Settings. The encrypted pairing state under `%LOCALAPPDATA%\MochiLog Windows` is kept when uninstalling so a reinstall can reconnect. The tested build host is Windows 11 build 26200, x64.

The build script requires Python 3.13, the .NET 10 SDK, and Inno Setup 6 on the **developer machine**. GitHub Actions builds the same installer and uploads it as an artifact. Test the transfer protocol with `dotnet run --project tests/ProtocolTests/ProtocolTests.csproj -c Release`.

## Transfer compatibility

Current mobile versions seal the entire authenticated transfer request, including acknowledgements, duplicate checks, and diagnostics, with AES-GCM as transfer v3. The request timestamp is valid for five minutes; used nonces and devices upgraded to v3 are stored in DPAPI-protected state so replay and downgrade are rejected after restart. Unauthenticated connections are limited to 16 concurrent clients and 25 seconds. Previously paired old mobile builds may use transfer v2 until they update; Windows then prompts for a TestFlight or App Store update. Independently updating either side does not remove the pairing. Old v2 requests have no timestamp, so full expiration enforcement begins with v3. The mobile app keeps separate pairings and acknowledgements for multiple computers, and a second computer cannot replace the device's physical ID. The transfer protocol has automated pairing, encryption, acknowledgement, and replay tests.
Before sending a log to a compatible mobile app, Windows offers its SHA-256 digest over the encrypted connection. A matching file already imported or awaiting import on that device is acknowledged without sending its bytes. Explicit manual resend bypasses this check; older app versions keep the existing transfer behavior.

Windows device discovery and log collection are being tested against iOS/iPadOS 27 with Apple Devices and classic iTunes. Initial OS trust setup uses a data cable, an unlocked device, and Apple's USB stack on the PC. The collector's `usbmux` commands talk to its local endpoint (port 27015). On the test Windows PC, that endpoint belongs to `AppleMobileDeviceProcess.exe` installed by Apple Devices. Apple Devices does not expose the unplugged device through the collector's usual Bonjour/usbmux discovery. The pinned collector therefore uses the existing OS RemotePairing record with the device IP to open an authenticated userspace RSD tunnel. This direct-IP collection path does not call the `usbmux` command, but independence after removing Apple Devices/iTunes has not been verified on a clean Windows installation. On a real unplugged iPad, the bundled collector read a diagnostic file and the app collector classified one battery log and excluded five unrelated files. Do not describe the installer as self-sufficient for first-time pairing or ship this as a dependency-free Windows release until a non-conflicting USB backend has been implemented and tested on a clean machine with no Apple device software.

MochiLog Windows supports Windows 11 (build 22000 or newer) only. The installer rejects Windows 10.

The in-app setup guide links to [Apple Devices](https://support.apple.com/guide/devices-windows/mchl5ded2763/windows) and the [classic iTunes EXE from Apple](https://www.apple.com/itunes/download/win64). Use one or the other; the Microsoft Store version of iTunes is not the classic installer required by the upstream collector. iCloud for Windows handles cloud data and is not a substitute for either device-connection app. The Apple iTunes URL currently redirects to Apple's `iTunes64Setup.exe`; do not replace it with a Microsoft Store listing.

After app pairing, authenticated requests from MochiLog update the saved device IP. A changed IP triggers a new collection attempt. The user may also set a paired iPhone/iPad IPv4 address manually in the Windows app. Windows network-address changes refresh its Bonjour advertisement; the mobile app can set a Mac/Windows host IP manually as a fallback. Collection still requires the device to be unlocked and reachable, and an IP change while the mobile app is closed cannot be learned until it connects again. Tailscale can deliver already queued files across networks; direct diagnostic collection over Tailscale is not yet verified.

## Development safety

Do not commit pairing keys, collected analytics logs, signing certificates, or support diagnostics. The packaged collector is built from a pinned `pymobiledevice3` version; its licenses must be bundled with releases.

## Current battery protocol (2026-10-07)

The production collector uses pinned pymobiledevice3 11.19.1 DiagnosticsService.get_battery(), not the independent research wire client. BatterySnapshot filters only CycleCount, DesignCapacity, FullChargeCapacity, NominalChargeCapacity, AppleRawMaxCapacity, root CurrentCapacity (percent) and IsCharging. Capacity fields can be nested in BatteryData; nested CurrentCapacity is not treated as percent. Missing, sentinel, invalid or fractional values are not substituted with zero. The revision is SHA-256 of canonical sorted scalar JSON, including the charging boolean, excluding timestamps and identities.

The subprocess emits core scalars and the complete typed battery entry through bounded private stdout pipes. Neither raw IORegistry replies nor filtered values are written to collector logs. LiveBatteryCache is memory-only and excluded from CompanionState, daily archives, support attachments and battery-log storage. Requests use the existing v3 AES-GCM request envelope, expiry, persistent replay protection, authentication, pairing identity and response AAD. Legacy version-1 core responses are unchanged. Opt-in detailsVersion 1 uses a separate SHA-256 over the exact canonical detailsJSON string; unchanged detail revisions omit the string. Each flattened field preserves its path, kind and text value (including 64-bit numbers and Base64 data). Details are limited to 256 KiB and the encrypted frame to 1 MiB. Acquisition output is not persisted. No log acknowledgements, daily completion state, import, iCloud or archive mutation occurs in this branch. Cached values are scoped to the authenticated target device.

Automatic acquisition is serialized with existing collection/pairing. Visible desktop cards or recent authenticated mobile requests trigger polling; failed acquisition backs off. Mobile polling runs only while enabled and foreground, honors cellular/Tailscale settings, and uses existing pairings and discovered/cached routes. Restart discards values. Unsupported older companions require an update, not a pairing reset. A successful current diagnostic query is not proof of locked-state Analytics file acquisition.

Verification: Python whitelist/revision tests; secure transfer protocol tests covering changed/unchanged/stale responses, no persisted values, and v3-only live controls; mobile iPhone/iPad opt-in and rotation tests; an isolated synthetic Mac server → iPad simulator v3 encrypted exchange. Fixtures have synthetic identities and values and never modify real pairings. The full Windows app also builds with zero errors/warnings.

Windowsの合成サーバーは`dotnet run --project tests/ProtocolTests/ProtocolTests.csproj -c Release -- --live-simulator`で起動できます。毎回専用のテスト保管先を使い、実ペアリング・実ログは読みません。10分で終了し、テストデータを削除します。2026-10-08、SSHのループバック転送を介したiPhoneシミュレータで、Windowsサーバーのv3暗号化要求・SHA-256照合・値の表示・値が同じ場合の再受信が成功しました。

Full-field verification: six Python tests, core/full-detail compatibility, changed/unchanged detail responses, 64-bit precision and tamper rejection. Tailscale acquisition was verified from Mac to iPad; this is not evidence of cellular-radio operation until that physical switch is tested. Mac learns only authenticated Tailnet socket peers in memory and tries the existing native path before a remote fallback. The mobile cellular permission remains opt-in.
